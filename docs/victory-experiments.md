# Victory experiment log

See [benchmarks](benchmarks.md) for the measured values and [upstream](upstream.md) for submitted changes. Variant names and retained test summaries are searchable in the [run index](../data/runs.csv) and [branch snapshot](../data/branches.csv).

## Wine and the prologue

1. **Launch the original runtime.** Cross-built VIctory in Toolbox and booted with stock Proton Experimental offline on RX 6800. Reproduced setup input and 4K presents. Built TuxBox in parallel and isolated its missing-CLWB failure on the Xeon.
2. **Package the Wine path.** Generated offline Cargo and xwin manifests. Split xwin, Victory, Proton and launcher modules. Built the Flatpak with the Wine base. Removed the X11 socket after a Wayland-only run, verified the read-only game mount, and reduced the borderless prototype to the source-side title change.
3. **Reach visible 3D.** Cleared an earlier texture read fault, tested indirect clamping, and used temporary geometry and render-target views to identify the opening street. Partial textures, narrower guarded copies, stride fixes and watchdog diagnostics each got isolated branches. Repeat tests often stayed on the loading artwork. The geometry-only capture was a diagnostic view with a fixed camera.
4. **Restore Series S presentation and bindings.** Tested the compositor, structured-buffer translation, larger dynamic descriptor ranges, lighting downsamples, stride and raw aliases. Restored UI and credits. The first combined 3D attempts still presented black or rendered incomplete geometry.
5. **Integrate the AMD donor stack.** Preserved `amd-view-heap` lineage and author information when combining shader warm-up, descriptor limits, a DXC fallback, dirty texture uploads at submission time, optional watchdog control and borderless mode. The dirty-texture change originated in Adrito’s [FX #80](https://github.com/fxceless/victory-fork/pull/80). The copied-window work went through [Marvisak #1724](https://github.com/Marvisak/VIctory/pull/1724) and [FX #131](https://github.com/fxceless/victory-fork/pull/131).
6. **Restore a game-generated checkpoint.** Probed optional intro skip and autosaves in an isolated prefix. The restore read both save blobs. A later controlled prologue run verified walking, turning the camera and pause/resume. Tests progressed through dialogue and the prison guard sequence. Other early 3D runs still had broken faces, missing geometry, bad lighting or loading stalls.
7. **Profile the renderer.** Tested ZSlayer relay and shorter pipeline waits, Fxceless asynchronous submit and copy queues, DXC for Wine HLSL failure, GPU-local compares, shader cache keys and separate pipeline workers. One DXC-enabled sample recorded seven copy-queue reads totaling 42.8 MB per frame. Copy work and pending pipeline waits remained large. Broad async comparisons drew different scenes or used disabled GPU-local copies, which limited comparison.
8. **Try narrower memory optimizations.** Compared 8 MiB and 1 MiB write-watch gaps, guarded host copies and writes, disjoint refreshes, sparse copy-back scans and batched physical-page mappings. Isolated tests showed several improvements. Different draw counts and small samples made the end-to-end cases inconclusive. See [isolated measurements](benchmarks.md#isolated-measurements-and-build-times).
9. **Track upstream without replacing the working probe.** Published linear Fxceless integrations with preserved author attribution, moved the canonical target to `gmankab/victory`, and mirrored distinct branches. The candidate on `f6a09d3b` built and passed 27 invocations. Later idle probes reproduced the same startup exception on canonical `d56316bb` and the latest stock Fxceless build. The earlier scripted test stopped on different setup pages. [Startup controls](benchmarks.md#fxceless-startup-controls) [Projects and mirrors](projects.md#published-branches)

## Wine-free Linux

1. **Run the title from ELF.** The early Linux ELF only handled inspection. Later Spidercraft builds executed the title through native PE loading, guest Windows ABI and native vkd3d-proton. REA verified the ELF, enumerated the PE imports and resolved crash frames and early API stops. CLWB and CLZERO compatibility required separate checks on this host. Early native builds with only the CLWB handling stopped at CLZERO; subsequent variants reached menus and loading.
2. **Separate hardware from software failures.** Native RADV menus reached about 30 FPS. Two early native vkd3d-proton revisions hit graphics-ring resets on heavy 3D submissions. A later run reached 0.5 FPS before a recoverable queue timeout. Driver breadcrumbs showed an invalid GPU read around the same compute dispatch even with descriptor heaps disabled, and DXIL validation rejected that shader. The shader validator fix passed targeted tests. Its result on the hardware reset remained inconclusive.
3. **Check the Linux ABI and loader.** Tested guest `GetProcAddress` and physical-page fixtures, mesh draw/readback, Bink intro ABI skip, optional watchdog diagnostics, guarded VM reads, imported CPU memory and correct memory type selection. A 64 KiB native RX 6800 readback was exact for anonymous memory. Shared `memfd` backing still failed. A headless mesh fixture matched all 256 expected pixels.
4. **Repair resource data flow.** Added or tested guest alias write tracking, disjoint resource refresh, staging bounds, upload order before rendering, untouched-pixel preservation, partial texture updates and clean texture tracking. RX 6800 and Lavapipe readbacks drove the regressions. An eight-mip BC7 test verified changed content reached the GPU in the same submission and unchanged data could be skipped.
5. **Control indirect workload.** Compared private indirect buffers, active-record clamps, underflow-safe budgets, scratch-state reuse, GPU-local scratch and GPU-local workload counters. Also tested skipping a clamp when its pipeline was unavailable and an extra barrier variant. Individual outcomes and cost tradeoffs are listed in [benchmarks](benchmarks.md#isolated-measurements-and-build-times).
6. **Restore display planes and inspect Wave32/Wave64 behavior.** Composited 1080p and 4K Series S display planes. Native Wave64 emulation cleared 128 rejections in that category; 96 Wave32 cases initially remained. Narrow fixed-wave fallback restored two, leaving eight hardware subgroup requirements and 86 unsupported translator cases in that comparison. The first-lane fix passed 96 shader tests but left the loading failure count the same. A later single-wave control-flow adaptation recovered 179 compute pipelines, from 419 to 598, preserving all 419 earlier ones. Forty compute shaders still failed translation and eight required a fixed 32-lane subgroup in that run. [Wave report](https://github.com/Marvisak/VIctory/pull/189#issuecomment-7184527098) · [Control flow source](https://github.com/Marvisak/VIctory/pull/233)
7. **Measure actual GPU work.** Fixed timing for single-list submissions and recovered prior-submission occlusion data. The occlusion fixture passed on RADV; the full run created four heaps but did not exercise measured readback. Lowering a broad shader loop cap, masking expensive shader pairs, and forcing point versus nearest-mip sampling isolated slow passes but frequently changed the image or left black output. Software worker counts 12 and 24 produced similar medians. [Timing PR](https://github.com/spidercraft/VIctory/pull/24) · [Occlusion discussion](https://github.com/Marvisak/VIctory/pull/1731)
8. **Isolate software BC7 cost.** Traced the expensive loading pixel draw to a trilinear BC7 sample. RADV and Lavapipe had very different costs for the same synthetic draw. A local Mesa 26.2.6 cache keyed on compressed BC7 block contents made warm software draws substantially faster and preserved exact readbacks. The game reached its first mesh bind sooner, but captures stayed on loading. [Posted details](https://github.com/spidercraft/VIctory/pull/24#issuecomment-7185812097)
9. **Diagnose Vulkan buffer views and storage.** Capped oversized constant-buffer views before staging. Tested a native vkd3d-proton null-descriptor fallback, then a 256 MiB storage-range test where oversized warnings disappeared while zero-range errors persisted. A separate Victory patch mirrored empty SRV/UAV views as null descriptors. Tests passed under Wine and native Linux. Full native warnings persisted, so a local vkd3d trace logged separate CBV, SRV and UAV inputs. Standalone fixtures showed how these three paths can issue a zero range. The longer matched title run logged 22 zero-byte constant-buffer requests, zero traced SRV/UAV causes, and nine Vulkan validation messages before timing out at 460 seconds. The host shadow and dynamic scratch paths could both turn empty views into nonzero addresses. The port of AscilCH’s null-CBV fix stopped both cases. The matched 460-second rerun logged zero of either warning and captured frame 750. It still ended during illustrated loading. [Native port](https://github.com/spidercraft/VIctory/pull/27) [Size bound](https://github.com/spidercraft/VIctory/pull/25) · [Empty SRV/UAVs](https://github.com/spidercraft/VIctory/pull/26)
10. **Verify audio ring boundaries independently.** Applied AnoHunted’s XMA read/write wrap fixes with the original author preserved. Seven native audio tests passed. The 460-second software title run still showed illustrated loading and the same descriptor warning count. A sampled stack was waiting in Lavapipe’s compute pool. [Source PR](https://github.com/Marvisak/VIctory/pull/536)

## Diagnostic boundaries

Some branches experiment with code paths intentionally isolated from a release build. Examples include skipping blocked draws, temporary geometry and target views, forcing shader-loop caps and samplers, disabling watchdog behavior in the mapped title, and adding logging to graphics libraries. Changes that preserve visible behavior and pass their own regression tests are tracked separately through the [PR index](upstream.md). Stable and controllable free roam at 30 FPS remains to be measured.
